# Web Deploy — GitHub Pages

Adapted from the "Web Deploy GitHub Pages" skill (ThomekSolutions) for **this** repository.
The upstream skill scaffolds a brand-new portfolio site, creates a repository with `gh`, and
pushes to a `gh-pages` branch. None of that applies here: AdShield Pro already has a marketing
site in `docs/`, a web platform at the repository root, one workflow that publishes both, and a
staging script that is the single source of truth for the layout. What is worth keeping from the
skill is the discipline around metadata, deployment checks, and rollback — that is what this
document encodes.

> Do not run the upstream `scripts/init_project.sh` / `scripts/deploy_github_pages.sh` here.
> They create a second repository, a `gh-pages` branch, and a competing workflow. This repo
> deploys with `actions/deploy-pages` and the `github-pages` environment.

## What gets published

| URL | Source | Notes |
|---|---|---|
| `/` | `docs/` | Marketing site, APK download links, privacy policy |
| `/app/` | repository root (`index.html`, `app.js`, `engine.js`, `sw.js`, `manifest.webmanifest`, `ui/ dns/ aether/ security/ assets/`, `omnishield-x-extension.zip`) | The OmniShield X web platform; relative URLs only, so it works from a subdirectory |
| `/404.html` | `docs/404.html` | GitHub Pages serves it for any unknown path |
| `/robots.txt`, `/sitemap.xml` | generated by `scripts/stage-site.mjs` from `docs/canonical.txt` | Never committed |

<https://yawiyuson231-oss.github.io/AdShieldPro/app/>.

The layout is produced by one script, not by the workflow:

```bash
npm run stage                 # writes _site/ exactly as CI does
npm run verify:site _site     # audits the staged tree, exits 1 on any broken gate
npm run serve                 # http://localhost:8080 for manual checks
```

## The pipeline

`.github/workflows/deploy-website.yml`, triggered by pushes to `main`/`arena/**` that touch
`docs/`, the web platform files or the workflow itself, and by `workflow_dispatch`.

```
checkout
  → site files present (docs/index.html, 404.html, og-image.png, canonical.txt, app entry points)
  → configure-pages@v5 (enablement: true — turns Pages on when the token allows it)
  → stage-site.mjs --out _site        (assembles /, /app/, 404.html, robots.txt, sitemap.xml;
                                       fails if a service-worker precache target is missing)
  → verify-site.mjs _site             (links, preview tags, 404, sitemap, size limits)
  → upload-pages-artifact@v3
  → deploy-pages@v4                   (needs: pages: write, id-token: write)
```

`adshield-release` also re-runs this workflow after publishing an APK (`gh workflow run
deploy-website.yml --ref main`), so the site's download links never lag a release.

## One-time setup (fork or new owner)

1. **Enable Pages once.** Creating a Pages site is the one deployment operation the default
   `GITHUB_TOKEN` is *never* allowed to perform, so this cannot be automated away with the
   workflow token. Pick one:
   - **Click it:** Settings → Pages → **Source: GitHub Actions**. Takes effect immediately; re-run
     the deploy workflow afterwards.
   - **Delegate it:** add a repository secret `PAGES_TOKEN` — a fine-grained PAT scoped to this
     repository with **Pages: read and write**. The workflow passes it to `configure-pages` with
     `enablement: true` and enables Pages by itself.

   Either way, the workflow's failure message names this exact choice rather than the action's raw
   "Create Pages site failed" error.
2. **Confirm the environment.** Settings → Environments → `github-pages` must exist (it is created
   on the first deploy). If protection rules were added, allow the `main` branch.
3. **Set the origin.** Put the published URL in `docs/canonical.txt` (one line, no trailing slash)
   and update the three absolute URLs in `docs/index.html`: `rel="canonical"`, `og:url`, and the
   `og:image` / `twitter:image` pair. The sitemap and `robots.txt` follow `canonical.txt`
   automatically; `verify-site` fails if any of them disagree.
4. **Register the social preview** once the site is live — GitHub's repository *Social preview*
   setting (Settings → General → Social preview) accepts `docs/og-image.png` and only takes effect
   for the repository page, not for `github.io`. Rendered previews cache aggressively; use a
   cache-busting query (`?v=2`) if an old image sticks.

## Verifying a deployment

```bash
# 1. Locally, on the same bytes CI will upload
npm run stage && npm run verify:site _site

# 2. Serve it the way Pages does — from a subdirectory, not from the filesystem root
npx http-server _site -p 8080        # then open /, /app/, and a bogus path for the 404 page
                                     # (the 404 page only works on Pages itself; a static
                                     # server returns its own)

# 3. After the workflow runs
gh run list --workflow deploy-website.yml -L 3
gh run view <id> --log
```

Checks that catch real regressions and are easy to forget by hand:

- `/app/` starts, and reloading it deep in the SPA still boots (service worker scope is `/app/`).
- The marketing page's "Web platform" link (`href="app/"`) — relative, never `/app/`, so it also
  works if the site moves to a custom domain.
- `robots.txt` and `sitemap.xml` return the declared origin.
- Run the whole thing after a version bump: `tests/unit/stage.test.mjs` fails if
  `omnishield-x-extension.zip` was not rebuilt for the new `package.json` version.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| *Create Pages site failed: Resource not accessible by integration* | Pages has never been enabled and the workflow token cannot create it | Settings → Pages → Source: GitHub Actions (or set `PAGES_TOKEN`), then re-run |
| Workflow fails at *Configure Pages* | Pages is enabled but Pages config is stale/locked | Re-run `configure-pages`; check the `github-pages` environment exists |
| *Deployment failed, try again later* | Pages environment protection or a concurrent deploy | Re-run; `concurrency: pages-${{ github.ref }}` already serialises per branch |
| 404 on every page but `index.html` | Pages built from a branch (`main /`) instead of the artifact | Set Source to **GitHub Actions**, not "Deploy from a branch" |
| Site loads, `/app/` is blank | A module or feed was not staged | `npm run stage` fails first — if it passed, check the console for a network 404 and add the file to `APP_ROOT_FILES`/`APP_DIRS` |
| `/app/` works online, not offline | A precache target is missing | `checkPrecache()` in `scripts/stage-site.mjs` names the missing entries |
| Old APK still linked after a release | Deploy workflow was not triggered | `gh workflow run deploy-website.yml --ref main` |
| Old preview image in Slack/X | External cache | Wait, or append a query string to `og:image` |

## Rollback

Pages serves one artifact at a time, so "rollback" is "deploy an older commit":

```bash
# Re-deploy the last known-good commit, without rewriting history
git switch -c revert/pages-<date> <good-sha>
git push origin revert/pages-<date>          # the deploy workflow runs on the push
# then open a PR from that branch and merge it

# Or revert the change on main and let the pipeline redeliver
git revert --no-edit <bad-sha> && git push origin main
```

`gh run rerun <id>` re-runs the same commit — use it for infrastructure flakes, never for bad
content. There is no `gh-pages` branch in this repository, so do **not** force-push one.

## Guardrails

- Never commit secrets. `.gitignore` covers `*.jks`, `*.keystore`, `.env*`, `signing.properties`;
  the release keystore lives in repository secrets `ADSHIELD_KEYSTORE_BASE64` /
  `ADSHIELD_STORE_PASSWORD`.
- Never deploy from a dirty tree: `git status --porcelain` must be empty, because the artifact is
  built from the checkout, not from your working directory.
- Never edit `_site/` by hand; it is generated and git-ignored.
- Do not add a `CNAME` file or change DNS without the owner's decision — a custom domain changes
  the origin in `docs/canonical.txt`, the sitemap, and every absolute URL in `docs/index.html`.
- Keep the artifact honest: `verify-site.mjs` fails on files over 100 MB (a Pages hard limit) and
  on dev-only files (`tests/`, `scripts/`, `node_modules/`, `package.json`) leaking into `_site/`.
